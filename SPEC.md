# Velt vault format specification

Status: version 2, pre-1.0. This document is the normative specification for
the `.velt.vault` file. The implementation lives in
`crates/velt-core/src/vault.rs`; cryptographic primitives are in
`crates/velt-core/src/crypto.rs`.

The key words MUST, MUST NOT, SHOULD, and MAY are used as defined in RFC 2119.

## Design goals

1. Every secret value is encrypted and authenticated independently.
2. Independent additions in different Git branches do not touch a shared
   revision, checksum, or timestamp line.
3. Unchanged entries serialize byte-for-byte identically across saves.
4. Key names, update timestamps, and expiry are visible to Git but bound to the
   ciphertext with associated data.
5. A wrong key, modified ciphertext, modified entry metadata, or modified team
   binding fails closed. An exported team vault binds its team id/epoch into
   every entry's AAD.

## Non-goals

- The format does not hide key names. Git history reveals the secret schema.
- It does not hide equality: the same key, value, timestamp, and expiry always
  produce the same ciphertext because AES-SIV is deterministic.
- It does not detect deletion of a complete entry line. Per-entry AEAD proves
  that present entries are authentic; it cannot prove that an absent entry was
  never present. Completeness requires Git commit signatures, a trusted remote,
  or the relay's version history.
- It is not a password vault. The vault key is a random 256-bit key held by the
  OS credential store, not derived from a human password.
- A local `.velt.vault` is not decryptable on another account; it uses the
  local OS-keychain key. `velt export` can write a separate team-key-encrypted
  file (`key_mode team`) that is decryptable by a teammate who has fetched the
  team key. The shared file does not embed member envelopes or the team key.

## File grammar

The file is UTF-8 text with LF line endings. Parsers MUST accept a trailing CR
before LF for compatibility. Lines are defined below; blank lines and lines
beginning with `#` are ignored.

```abnf
vault        = magic LF
               id-line LF
               created-line LF
               key-line LF
               [ key-mode-line LF ]
               [ binding-line LF ]
               *entry-line
magic        = "VELT-VAULT 2"
id-line      = "id " 32HEXDIG
created-line = "created_at " POSITIVE-DECIMAL
key-line     = "key_version " POSITIVE-DECIMAL
key-mode-line = "key_mode local" /
                "key_mode team " UUID " " POSITIVE-DECIMAL
binding-line = "binding " BASE64URL-NOPAD
entry-line   = "ENTRY " name SP updated-at SP expires-at SP BASE64URL-NOPAD
name         = (ALPHA / "_") *(ALPHA / DIGIT / "_")
updated-at   = POSITIVE-DECIMAL
expires-at   = "-" / NONNEGATIVE-DECIMAL
NONNEGATIVE-DECIMAL = "0" / POSITIVE-DECIMAL
POSITIVE-DECIMAL = %x31-39 *DIGIT
BASE64URL-NOPAD = 1*(ALPHA / DIGIT / "-" / "_")
UUID         = 8HEXDIG "-" 4HEXDIG "-" 4HEXDIG "-" 4HEXDIG "-" 12HEXDIG
```

- `id` is the 16-byte vault id in lowercase hexadecimal. It MUST match the
  decrypted payload.
- `created_at` is Unix seconds. It MUST be positive.
- `key_version` is currently `1`. Readers MUST reject other values with an
  unsupported-version error.
- `binding` is optional. When present it is the AES-SIV ciphertext of the
  compact JSON `RemoteBinding` object.
- `ENTRY` lines SHOULD be sorted by name in bytewise ascending order so that
  writes are reproducible. Readers MAY accept any order but MUST reject
  duplicate names.
- `expires_at` is `-` for no expiry, otherwise Unix seconds. It MAY be negative
  for an already-expired value.
- Names MUST be 1–256 bytes and match `[A-Za-z_][A-Za-z0-9_]*`. Values MUST be
  valid UTF-8, contain no NUL byte, and be at most 1 MiB. A file MUST be at most
  16 MiB and contain at most 100,000 entries.

The parser MUST reject unknown non-comment lines, duplicate `id`,
`created_at`, `key_version`, or `binding` lines, missing mandatory lines, and
decryption/authentication failures.

## Cryptographic parameters

### Master / team key

A local vault uses a 32-byte master key generated by the OS CSPRNG and stored
in the OS credential store under `vault:<vault-id>`. A team-mode vault uses the
32-byte team key for the epoch named in `key_mode team <team-id> <epoch>`; the
team key is stored in the OS credential store under
`team-key:<team-id>:<epoch>` after a relay envelope fetch. Neither key is
written to the vault file. Recovery shares encode whichever key unlocks the
file.

### SIV key derivation

```text
SIV_KEY = HKDF-SHA256(
    ikm  = MASTER_KEY or TEAM_KEY,
    salt = "velt-vault-siv-salt-v2",
    info = "velt-vault-siv-key-v2",
    L    = 64
)
```

The 64-byte result is the key for AES-256-SIV (RFC 5297). HKDF is used for
domain separation, not password stretching. The key is zeroized after use.

### Entry nonce

```text
ENTRY_NONCE = SHA-256(
    "velt-vault-entry-nonce-v2|" || hex(VAULT_ID) || "|" || name || mode_suffix
)[0..16]
```

`mode_suffix` is empty for `key_mode local`, otherwise
`|team|<team-id>|<epoch>`. AES-SIV is misuse-resistant. The nonce is
deterministic so that unchanged entries are byte-identical; nonce reuse leaks
equality but does not break confidentiality or integrity.

### Entry associated data

```text
ENTRY_AAD = "velt-vault-entry-v2|" || hex(VAULT_ID) || "|" || key_version
            || "|" || name || "|" || updated_at || "|" || expires_at
            || mode_suffix
```

`expires_at` is the decimal value or `-`. The clear-text metadata on the
`ENTRY` line is therefore authenticated. Changing any of it makes decryption
fail.

### Entry ciphertext

```text
ciphertext = AES-256-SIV-Encrypt(SIV_KEY, ENTRY_NONCE, ENTRY_AAD, value)
encoded    = base64url-no-padding(ciphertext)
```

AES-SIV returns its 16-byte authentication tag followed by the ciphertext. The
implementation treats the whole byte string as opaque and base64url-encodes it
without padding.

### Team binding

```text
BINDING_NONCE = SHA-256(
    "velt-vault-binding-nonce-v2|" || hex(VAULT_ID) || mode_suffix
)[0..16]
BINDING_AAD   = "velt-vault-binding-v2|" || hex(VAULT_ID) || "|" || key_version
                || mode_suffix
ciphertext    = AES-256-SIV-Encrypt(SIV_KEY, BINDING_NONCE, BINDING_AAD,
                                    compact_json(RemoteBinding))
```

The binding object is:

```json
{
  "team_id": "uuid",
  "environment": "production",
  "epoch": 2,
  "base_version": 14,
  "base_checksum": "optional hex"
}
```

`team_id` and `environment` MUST be non-empty. In a team-mode vault the binding
`team_id` MUST equal the `key_mode` team id. The binding is encrypted because
team and environment identifiers are not required for Git-level merging.

## Merge semantics

- Header lines are stable for the life of the vault. There is no global
  revision, checksum, or updated-at line, so a save that changes only one entry
  does not modify the header.
- Every entry is one line. Disjoint additions and edits merge with ordinary Git
  line merging. A conflict means two branches changed the same entry, which is
  a semantic conflict and MUST be resolved by a human.
- Duplicate names after a merge are invalid. Do not sort-union duplicate lines;
  resolve the conflict and load the file again.
- The format does not store a global MAC. An attacker who can rewrite the file
  can delete an entry, but cannot forge a modified entry or metadata without
  the key.

## Team-mode files

`key_mode team` files are produced by `velt export` and use the shared team key.
The header team id/epoch is public; the team key is not in the file. A reader
must obtain the matching key (for example `velt team key-fetch --team <id>`)
before calling the vault loader. Changing the header team id/epoch or moving an
entry between team files makes AES-SIV authentication fail.

A shared file does not detect deletion/rollback any more than a local file. A
teammate who already possesses the file and key can decrypt it after revocation;
rotate the team key and re-export.

## Legacy format 1

Version 1 used a binary `VELTVLT1` header, a 12-byte ChaCha20-Poly1305 nonce,
and one ciphertext containing a JSON payload with a checksum. Version 2 readers
detect the magic and decrypt v1 files with the same master key. The next save
writes version 2. There is no downgrade path; back up the v1 file before
migrating if a v1 reader is still required.

## Test vector

Inputs:

- master key: 32 bytes of `0x42`
- vault id: 16 bytes of `0x11`
- created_at: `1700000000`
- key_version: `1`
- entry: `API_KEY` = `secret-value`, updated_at `1700000001`, no expiry
- no binding

Expected file:

```text
VELT-VAULT 2
id 11111111111111111111111111111111
created_at 1700000000
key_version 1
ENTRY API_KEY 1700000001 - APFtI1nW4Wke0QsGolKTP17vcZN6DibnldrfSQ
```

This vector is enforced by `vault::tests::known_answer_vector`. Team-mode vectors
are covered by `team_mode_export_roundtrip` and `tampered_team_mode_fails_closed`.

## Compatibility policy

Any incompatible change increments the format version. Readers MUST reject a
newer version instead of guessing. The binary format is not a stable API for
other implementations until the specification reaches 1.0.
